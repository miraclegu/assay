# 策略与回测 —— 踩坑详情

正本索引在 `assay/CLAUDE.md`。**做策略实验、改引擎或参数之前**读这一册；里面每一节都是实测定案（有现场、有判据、有变异结果）。

## 🔴 策略数据 API：让策略不必直接写 SQL（2026-09-07 新增，现有策略未动）

理想中**只有 feed 知道 datalake 的存在**。而 froec.py / 红利那批把 9 层 CTE
写在策略文件里：口径（as-of / 停牌结转 / 多期去重）与规则（阈值 / 分位 /
排序 / 截断）混在同一段文本里，换数据源、改口径、复用某一层都无从下手。

`assay/feed.py` 新增三个取数方法（`assay/guard.py` 逐个转发并加 PIT 检查）：

| API | 干什么 | 关键口径 |
|---|---|---|
| `universe(date, listed_days, exclude_like, perturb, salt)` | PIT 在册股票 | 🔴 **不是面板当日行** —— 停牌股当日无 K 线、无行，而它们要参与分位切点的计算 |
| `snapshot(date, cols, codes, carry_days)` | 面板当日行 + 停牌结转 | 🔴 **只结转价格派生量**；基本面不结转（会拿到该股最后交易日的过期报告） |
| `fundamentals(date, fields, codes, periods, require_all)` | 按 `pub_date` as-of 的财务，可取最近 N 期 | `require_all=True` 只留凑满 N 期的 —— 缺期的票会算出偏小的值而**不报错** |

**职责边界**：feed 管「从哪取、as-of 怎么算」，策略管「阈值、分位、排序、
截断」——后者是规则，本来就该看得见、改得动。

验证用新策略 `strategies/小市值/froec_api.py`：用 API 取数 + pandas 写规则，
**不含一行 SQL**。它通过 `importlib` 独立加载 froec.py 的**私有实例**，
只在这个实例上替换 `rebalance` —— `module_from_spec` 每次都是新对象，
所以 froec.py 的其它使用者（froec_traded.py、实盘快照）完全不受影响
（同 froec_traded.py 的做法）。
★ **froec.py 一行没动**：它的归档要可比，而且实盘账户绑着它的快照。
  selftest 里两向都钉：froec.py 里不许出现新 API、froec_api.py 里不许有 SQL。

### 🔴 顺带发现：原 SQL 在 ROE 切点并列时【结果不确定】

`ORDER BY r.increase DESC` **没有 tie-break**，而 `roe_inc` 只有 4 位小数、
并列很常见。当并列**恰好跨过切点** `floor(0.1 * n2)` 时，谁进谁出取决于
DuckDB 的扫描顺序 —— **原 SQL 自己就不保证跨机器/跨版本稳定**。

实测（539 个调仓日，抽样 77 个）：切点并列 3 个 = 3.9%；
其余 74 个与 API 版**候选池逐位相同 74 / 不同 0**。

★ API 版三处排序都加了**显式 tie-break（按代码）**：至少它自己可复现。
🔴 **没有去"修" froec.py 的排序** —— 那会改变它全部历史归档的结果。
  这个不确定性值得单独记一笔，但不该顺手改掉。

★ 诊断时踩过两个坑，都值得记：
① tie 检测写在**行业排除之后**的结果上 —— 被排除的那一行不在末层输出里，
  查 `roe_rn == cut+1` 就漏判成"无并列"。检测"切点两侧是否相等"必须在
  **截断与排除之前**做。
② 断言只比 `jq_code` 列表**太松**：切点算错 ±1 只多/少带一只票进半区，
  而它常常本来就进不了最终前 20 -> 断言照样绿。要连**中间层的分母**
  （`pb_n` / `roe_n`）一起比 —— 那才是切点的硬证据。而**名次**
  （`pb_rn` / `roe_rn`）只在整列无并列时可比。
③ 采样日要够密：6 个采样日抓不到 "roe 切点 -1"，加到 16 个才抓到。


### 持仓表按列排序（2026-09-11）

点表头在【当日 / 当日盈亏 / 市值 / 浮盈 / 幅度 / 仓位】之间切换，再点一次反向。

★ **首次点击给降序** —— 这六个都是「越大越好」的量，人点它是想看"最赚的/
  最大的是哪个"（同回测页「★ 选中的规则」那条：换列时默认方向按**哪边更好**给，
  一律升序会把最差的排最前面）。
🔴 **`LVSORT` 必须是模块级**：`loadLive` 每分钟重渲染一次，存在局部里的话
  刚点的排序立刻被冲掉。
🔴 **`null` 一律排最后**（不管升降序）—— 停牌股取不到价，那几行的当日/浮盈
  都是 null。把 null 当 0 参与排序的话它们会混在正负之间，看着像"这只票今天
  不涨不跌"，而事实是**没有数据**。
★ 与原地刷新（`livePatch`）**天然兼容**：patch 靠 `td[data-rt="code|field"]`
  找格子，与 DOM 行序无关。所以排序后那 60 秒的自动刷新照样只换数字、不重排。
  selftest 两向都钉：quiet 刷新与全量重渲染都不许改行序。
★ **不持久化到 localStorage**：排序是"我现在想看什么"，下次打开该回到默认
  （同「待办折叠状态不持久化」那条）。

🔴 **给 `Bar` 加列要改【三处】，漏一处的表现各不相同：**

| 漏哪处 | 表现 |
|---|---|
| `_BAR_COLS`（SQL） | 建表就少这一列 —— 立刻报错，最安全 |
| `guard.current()` | **策略侧永远收到 None -> 规则整段空转，且不报错**。加 `change_pct`/`ma5` 时漏过一次，是靠「四档参数跑出完全相同的结果」这个反常现象才发现的 |
| selftest 里手工构造 `Bar` 的桩 | `TypeError: missing N required positional arguments` —— 会报错，但**第二次**才想起来（加 touch_up 时补过，加 change_pct/ma5/ma20 时又漏） |

### 🔴🔴 炸板离场放宽到「盘中板」：两个变体都**不采纳**（2026-09-10）

现状（`froec_traded` 的 `check_limit_up`）只管**一类**票：
昨天**收盘封住**（面板 `is_limit_up`：close == 涨停价）→ 今天 14:00 没封住 → 清仓。
所以「昨天/今天盘中摸到涨停、尾盘炸了」的票**完全不管** —— 它 `is_limit_up=false`。
（实测 2026-09 以来「盘中摸到、收盘没封住」有 183 个交易日·票，`is_limit_up` 全是 false。）

两个变体（都是**新文件**，`froec.py`/`froec_traded.py` 一字节未改）：

| 文件 | 规则 |
|---|---|
| `froec_lu_intraday.py` | 昨天盘中摸到、收盘没封住 → **次日**卖 |
| `froec_lu_sameday.py` | **今天**盘中摸到、尾盘没封住 → **当天**卖 |

为此给 `Bar` 加了 `touch_up`（`high >= 涨停价`，与 `limit_up` = 收盘封住是两件事），
`guard.current()` 在 INTRADAY/CLOSE 相位给出它。**纯投影改动**：`git worktree`
检出改动前版本对跑，froec_traded 与红利指数增强的权益指纹 + 成交指纹 + 三项指标
**全部一致**。

#### 结论（逐年独立，vs 现状）

    次日卖              均 +0.43pp  中位 +0.60  更好 6/11  sd  6.12  t=+0.23
    当天卖（无抑制器）    均 +1.43pp  中位 +0.44  更好 6/11  sd  7.24  t=+0.65
    当天卖（补齐抑制器）  均 +0.47pp  中位 -0.26  更好 5/11  sd 20.62  t=+0.08

#### 🔴🔴 关键发现：**卖出判据与「再买抑制器」判据必须是同一个**

「当天卖」的第一版**规则不自洽**：

    卖出用    `touch_up`（盘中摸到涨停）且 `limit_up=false`
    黑名单用  `had_limit_up()` -> SQL 的 `AND limit_up` = **收盘封住**

两个判据**互斥** —— 被这条规则卖掉的票 `is_limit_up` 一定是 false，
所以 `had_limit_up` 永远查不到它，**卖出完全没有对应的买入抑制**。
实测全程炸板卖出 269 笔里 **37 笔在 10 个自然日内又买回来**（现状 **0 笔**），
其中 5 笔是「周一卖、周二买」—— 而周二正好是调仓日（`weekday=2`）。
★ 用户当场问「为什么会在第二天就买入？不是调仓日也会买入吗？」—— 逐笔查周内
  序号，7 笔无一例外都是**调仓日买入**（第 2 个交易日）。不是引擎异常，是规则漏洞。

补齐之后（`g.sd_banned`，窗口同 `limit_days`=20 交易日）：10 日内买回 37 → **0 笔**，
规则自洽了。**但效果反而更差**：

    均差 +1.43 -> +0.47pp    中位 +0.44 -> **-0.26**（由正转负）
    sd   7.24  -> 20.62      2024 那年 +16.31 -> **+0.40pp**

🔴 **所以那 +1.43pp 相当一部分恰恰来自那 37 次「卖了又买回」** —— 不是「躲开
下跌」的收益，而是在同一只票上做了一次**日内低买高卖**（卖在炸板价、次日买回）。
而回测「14:00 用收盘价代理」的偏差正好让这种操作系统性偏乐观。
🔴 补齐后更差的机制也清楚：抑制器把票锁在场外 20 个交易日 ≈ **4 个调仓周期**，
即使它排名一直在前 10 —— 那是**主动偏离目标池**。原版黑名单没这问题，因为它
锁的是「收盘封住过」的票，那种票次日往往高开、本来就不该追。

★ 这是 CLAUDE.md 里那条纪律的另一半：
  「卖出问的是『它还够好吗』，**黑名单是『再买』的抑制器**」——
  **加一条卖出规则时必须同时想清楚它的抑制器是什么**，否则就是「今天卖、
  明天买」的自相矛盾；而补上抑制器又可能因为锁太久而更差。
  两条都试过之后仍然不显著 → **这条规则没有可靠的机制**。

★ 包装 `blacklist` 本身而不是改调用点：froec 里它被调用 **2 次**
  （`rebalance` 与 `hold_buffer_strict`），改一处漏一处的表现是「缓冲区那条
  路径还是旧口径」，而它不报错、只是两条路径对同一只票给出不同结论。

#### 🔴 `exit_time` 在 14:00 与 14:55 **没有任何区别**

引擎无分时线，`_phase()` 把 `09:30 < t < 15:00` 全归为 `INTRADAY`，
同一相位读到的 `touch_up`/`limit_up` 都是**当日收盘**派生量。
实测 `13:30 / 14:00 / 14:55` 三个时刻**结果完全相同**（31.74%、79 笔、胜率 51.90%）。
★ 所以「挪到 14:55 去削掉那个偏差」是**无意义的验证** —— 我提过这个建议，
  被用户一句「现在我根本没有分时数据」问住。
★ 那个偏差（回测会卖掉一些 14:00 后回封的票）**在没有分时数据的前提下无法
  用回测消除**，只能明确记下来；方向是**乐观的**。
★ 但它不是新问题：现状那条规则在 14:00 读的 `limit_up` 同样是收盘派生量 ——
  两版站在**同一个近似**上，所以它们之间的比较仍然有效；不能外推的是
  「这个绝对收益在实盘能拿到多少」。

### 🔴🔴 第五个变体也**不采纳**：尾盘买入（`froec_close.py`，2026-09-19）

用户：「复制现有实盘的小市值策略，改成每周第一、二交易日的尾盘买入，
其他逻辑不改」——澄清后是**两次独立回测**（周一档 / 周二档，选股+卖+买
都在尾盘），不是一周做两次。

🔴 **在这个引擎里，"尾盘"的实质是【用当日收盘价成交】。**
  没有分时线，`_phase()` 把 `09:30 < t < 15:00` 全归 INTRADAY、一律用
  **当日收盘价**；而 `09:30` 属 OPEN、用**开盘价**。所以 14:00 与 14:55
  的成交价完全相同（记过一次，别再试），真正被改变的只有
  **开盘价 -> 收盘价** 这一件事。取 14:55 的唯一理由是**任务顺序**
  （排在 exit_time 的炸板离场与 stop_time 的止损之后）。

#### 🔴 机制是可量化的 —— 不是"运气不好"

笔数 903/907、885/897，年换手 9.65/9.62、9.16/9.92 —— **几乎相同**，
所以差异不是"交易变多变少"，是**每一笔的成交价**。
面板实测（2016 起，每日流通市值最小 300 只的 `close/open - 1`）：

    周内第 1 个交易日   均值 +0.129%   中位 +0.380%
    周内第 2 个交易日   均值 +0.235%   中位 +0.328%
    第 3 / 4 / 5 日     +0.049% / -0.075% / -0.093%

—— **恰好前两日最贵**，而那正是这个策略调仓的两天。每次贵 0.13~0.24%、
年调仓约 50 次，再经十年复利，就是这 7~9pp。

🔴 **「费用少了」是假象**：9.5 万 -> 6.7 万看着像优点，其实是**资金少**
（期末 191 万 vs 401 万，费用按成交额收）。换手一点没降。
  同「对数表里不许留只有数、没有判断的行」——这一行必须给判断。

#### ★ 做法上的两条

★ **一个字都没复述 `froec_traded` 的参数**：`importlib` 私有加载 + 转发
  （同 froec_traded 加载 froec 的做法）。凭印象拼 `_TRADED = {...}`
  是本项目作废过一整批结论的坑。
🔴 **等价性自证**：`--param rebal_time=09:30` 时本版与 `froec_traded`
  的逐日权益指纹**逐位相同**（`42e8994fe108`）——它证明"差异只来自时点"，
  而不是转发漏了什么。这一步不能省。
★ 参数默认值写成**字面量**而不是模块级常量：看板的参数解析只认
  `getattr(g,'x',字面量)`，用常量的话这一项在回测页上**看不见**。
★ 四次归档都**标星并写明结论**（`picks.json`）——标星同时是保护
  （`prune_runs` 一律不删），下次有人再想起"要不要尾盘买"时跑一行就能看到。
🔴 标星时**又凭印象猜了字段名**：写成 `kind: star`，而既有条目是
  `mark: star` —— 那样标星**静默失效**（`prune_runs` 与「★ 选中的规则」
  都读 `mark`），保护等于没有。写之前对一眼既有条目的形状。

### 🔴 第三、四个变体也**不采纳**：炸板分档跟踪 / 黑名单换成偏离度（2026-09-13）

同一条线索上又试了两个，基线统一为 `froec.py` 带 `lu_buy_only=1`：

| 文件 | 换了什么 | 逐年均差 | 中位 | 胜 | t |
|---|---|---|---|---|---|
| `froec_lu_trail5.py` | 炸板**按当日涨幅分档**：<5% 立刻卖，≥5% 转 MA5 跟踪 | +3.80pp | +1.47 | 6/11 | **+0.46** |
| `froec_devban.py` (0.13) | 黑名单判据从「涨停过」换成「**现价离 MA20 多远**」 | +1.94pp | +3.73 | 6/11 | **+0.41** |
| 同上 (0.10 / 0.08 / 0.05) | 阈值收紧 | +0.44 / +0.39 / **−2.91** | | | ≤0.07 |

**trail5**：全程（2016-01-01~2026-09-11，同数据同参数）39.07% vs 基线 38.74%，
只多 +0.33pp，而**费用多付 11.4 万（+31%）** —— 收益不确定、成本确定。
效应几乎全来自两个互相抵消的极端年（2016 +54.09 / 2026 −54.48）。
🔴 `lu5_ban=0` 看着更好（41.91%），但那 263 笔 intraday 卖出里 **39 笔
10 日内买回**（带抑制器与基线都是 0 笔）—— 与 `froec_lu_sameday` 那次
「+1.43pp 来自 37 笔卖了又买回」**完全同形**，收益来自回测用收盘价代理 14:00
所偏乐观的日内往返，不能当收益。

**devban**：四档的方向是**单调「越松越好」**，收紧到 0.05 直接为负。外推的极限
就是"根本不要这个黑名单"—— 与 PB 那一层的「收紧一致有害、放松无益」同形。
去掉两个极端年后 0.05/0.08/0.10 全部回到 0 附近或为负。
★ 规则**确实在起作用**（平均笔数随阈值 75.9 → 89.6 单调升、跨过基线 80.8），
  不是空转。所以这是"测出来没用"，不是"没测到"。
★ 出发点的推理都成立（「涨停过没有」是离散粗糙的代理、「离 MA20 多远」是连续的），
  而数据给的是 t ≤ 0.41 —— 同「ROE 加速度不合理的地方正是它有效的地方」：
  **指标看着更合理，不是采用它的理由**。

### 🔴 取归档对数：必须按【参数 + 区间】精确匹配，不能按标签取

这一轮差点把两个结论都写错，而且**两次都不报错**：

① **一个 `--group` 标签下可能有多次归档。** `_bo<年>` 里同时躺着
  `lu_buy_only=0` 和 `=1` 两次，我两个脚本一个取了 `glob` 的首个、一个取了末个
  —— 同一个"基线"给出 2016 年 25.64% 和 16.57% 两个值。是两次跑出来
  **对不上**才发现的；只跑一次的话会直接拿错的基线写进结论。
② **区间也要核**。基线 `_bo2026` 截到 **09-03**，而变体截到 **09-08** ——
  而 2026 正是主导结果的那一年（年化外推在 8 个月窗口上对几天极敏感）。

### ②🔴🔴 修好之后暴露的真问题：同一份代码同一份数据，结果跨进程不一样

    随机种子（默认）  10 个进程 -> 两种结果**各 5 次**

成因在 `etf_p1_rotation.py:461`：`sorted([s for s in in_trend ...], key=...)`
的 `in_trend` 是个 **`set`**，而排序键**并列时没有 tie-break** ——

🔴 **后果比"模拟盘推不动"大得多**：

    模拟盘  每次从起点重放再逐笔对账 -> 一半概率报「对账不一致」，
            而它给的原因是"数据被修正过" —— **指不到真正的原因**
    归档    同一个 run 重跑一遍结果就不同 -> 等价性回归、与聚宽对数、
            「同参数重复跑必然逐位一致」那条去重判据**全部失效**，
            **而它不报错**

**修法：不改策略，在外面固定种子**（`assay/hashseed.py`）。
四个可执行入口（`run.py` / `serve.py` / `tick_daily.py` / `selftest.py`）
第一件事调 `ensure_fixed_hash_seed()`：没固定就带上环境变量
**把自己重启一次**（`os.execve`），幂等。
★ 不改策略的理由与「没有去修 froec.py 的排序 —— 那会改变它全部历史归档的
  结果」是同一条：那是移植件，改排序会改变与聚宽正本的对数。
⚠ `PYTHONHASHSEED=0` 关掉的是哈希随机化（本是防 web 服务被构造碰撞键 DoS）。
  本项目是本地自用、不接受外部输入，这个取舍是明知的。

🔴 **判据必须是 `sys.flags.hash_randomization`，不是环境变量。**

  "已经固定了"直接返回 —— 而随机化**还开着**，回测照样不可复现且一声不吭。
  变异实测抓到（而"幂等判据加一个环境变量条件"那条是**无效变异**：

🔴 **`sys.argv` 不能用来 re-exec，要用 `sys.orig_argv`**：`python -c '...'`

  `Argument expected for the -c option`（第一版就是这么写的，当场被自证抓到）。
🔴 **必须是入口的第一条可执行语句**：exec 会把进程映像整个换掉，

  「前面只许有 docstring / import / `sys.path.insert`」。

★ 我的"确定性测试"第一版是**一个进程里跑 3 次** —— 那只证明了进程内可复现，
  什么都没证。**跨进程的问题必须跨进程测。**

## 🔴🔴 froec 三层结构的因子归因：**没有一个参数值得改**（2026-09-10，五轮实验）

那三个数原本只是从聚宽抄来的。这一轮把每层的贡献量出来了，结论是**原版已接近最优**。

全部实验都用**新策略文件**（私有实例，`froec.py` / `froec_traded.py` **一个字节没改**）：

## 回测纪律

- **逐年独立回测**（每年重置本金）才能比较规则；全程回测切片比对逐年差异测的是
  路径混沌不是规则 —— 零触发年份也能差 8.42pp
- 滑点**默认值**，只有对标聚宽时才设 0
- 改了引擎必须跑等价性回归 —— `ast.parse` 通过不代表逻辑没坏。
  🔴 **等价性比【数值】不比 parquet 字节**:`equity.parquet` 的字节含压缩与
  元数据,**内容相同也可能字节不同**(实测踩到:同一份 equity 前后两次归档,
  0 行数值差、字节 hash 不同)。判据用逐日曲线的数值指纹:
  `md5(string_agg(date || ':' || round(total_value,2), '|' ORDER BY date))`。

#### 🔴 真正的问题不在这四个口径里 —— 黑名单在**卖票**,而它不该卖票

| 同比 `roe₁−roe₅` | 24.12% | 0.933 | **−23.10pp** | **−2.80** | **0/11** |
| TTM `Σ₁₋₄−Σ₅₋₈` | 21.13% | 0.829 | **−28.40pp** | **−4.75** | **0/11** |

去掉 2026（只 8 个月）仍显著：−15.33pp (t=−5.08) / −23.52pp (t=−6.15)。
**这是本项目第一个 |t| > 2.23 的结论** —— 此前测过的所有开关（`limit_up_exit` /
`fill_paused` / `hold_buffer` / 黑名单五口径）都不显著。

★ **事实没错，因果判断错了。** 那个 63.9% vs 4.8% 是可验证的；但它**不是缺陷**。
  一个说得通的解释：大额减值常常是"一次性洗澡"，洗完之后基本面改善而市场
  还没反应过来 —— 小市值 + 低 PB + 刚洗过澡，是典型的深度价值反转组合。
  而"同比改善"选的是平稳增长的公司，在小市值池里那不是 alpha。
🔴 **不要拿"指标看起来更合理"当采用理由。** 从口径分析（单季 vs 累计、Q4 左尾、
  63.9% vs 4.8%）到"应该改用同比"，每一步推理都成立，而回测给出的是 **0/11**。
★ 两个策略文件**保留不删**（`froec_roe_yoy.py` / `froec_roe_ttm.py`，
  docstring 里带这张表）—— 同「已否证的规则留成开关，不要留成注释」。
★ TTM 那版还有个**混杂因素**要记：它要 8 期齐全，池子从 1629 缩到 1617，
  于是两个 `floor()` 切点都跟着挪 —— 它的差异不只来自 ROE 那一层。

## 🔴🔴 a2 与 froec 差 2.00pp：**全部**来自「绑定时没填参数」（2026-09-29）

用户问「FROEA-TRADE模拟账户和 FROEC-TRADE 账户的收益率差异非常大，最主要的
差异是哪里带来的」。答案是**参数**，而且能逐环钉死。

### 对照设计：a6 是干净的对照组

| 对照项 | a2 | a6（同参对照）/ froec |
|---|---|---|
| `init_cash` | 400000 | 400000 |
| 策略文件 sha | c3118f7d | c3118f7d |
| 建仓那 10 笔 | — | **逐笔完全相同**（代码/股数/价格全等） |
| **绑定 params** | **`{}`** | 显式五个 |

a6 建好之后与 froec 逐日 nav 只差 0.002~0.003 —— **对照组成立**，
所以剩下那一条差别（params）就是全部原因。

### `params={}` 会静默走策略默认，而默认与实盘在用的差很远

读策略文件本身（**不许复述参数**）：

| 参数 | 策略默认（a2 实际在跑） | froec/a6 显式绑定 |
|---|---|---|
| `stop_loss` | **0.0 = 止损关闭** | 0.35 |
| `lu_since_start` | **0 = 涨停回溯跨到建仓日之前** | 1 |
| `lu_buy_only` | 0 | 1 |
| `stop_intraday` | 0 | 1 |
| `weekday` | 2 | 2（相同） |

### 触发链：一天，两只票

- `301152` **2026-08-24** 涨停 +20.02%
- `603506` **2026-08-19** 涨停 +10.0%

两次都在建仓日 09-01 **之前**。要卖掉它们，**两个开关缺一不可**：

| 开关 | a2（默认） | froec/a6 | 少了它会怎样 |
|---|---|---|---|
| `lu_since_start` | 0 = 回溯**跨过建仓日** | 1 = 只从建仓日起算 | =1 则那两次涨停根本看不见 |
| `lu_buy_only` | 0 = 黑名单**有卖出副作用** | 1 = 只抑制买入 | =1 则看见了也只挡买、不卖 |

🔴 **别把功劳记在一条上**：只有 `lu_since_start=0` 让涨停可见、
`lu_buy_only=0` 把"可见"变成"卖出"，两条一起才产生这两笔。

★ 这件事 `froec.py:379` 的注释**早就记着**：

> 实盘 2026-09-08 的例子最能说明：被剔掉的两只排名是**第 3 和第 7**，
> 稳稳在前 10 名内 —— 按"它还够好吗"根本不该卖。

也就是说 `lu_buy_only=1` 本来就是为了修这个而加的。这次是**独立复现**，
顺带证明了它确实修好了（froec/a6 留着、a2 卖了）。

逐日 nav：09-08 之前两者**小数点后 4 位完全相同**，09-08 分叉（−0.34pp），
之后单调扩大到 **+2.00pp**（20 个交易日）。

🔴 **排他性也量了**：窗口内抽查的其它持仓一次涨停都没有 —— 正好只有被卖掉
的这两只。第一版假说是"09-08 前后涨停"，查出来**那两天都没涨停**，
假说当场作废；改查建仓前 28 天才对上。**差点把功劳记在错的那句上。**

### ⚠ 这同时推翻了我之前给过的一个结论

我说过「那四个参数改了都不影响窗口内结果」。那是**被 zsh 不分词坑污染的
假结论** —— `--param` 从 shell 变量拼出来时被当成**一个**参数，静默拒绝，
几轮当然跑出一模一样的结果。现在有直接反证：同样这四个参数造成了 2.00pp。

**没量过的数不许拿出来当对照** —— 而"量过了但量错了"比没量更糟，
因为它带着数字，看着像证据。

## 🔴🔴 徐倬迅「弹簧理论」：三级 × 个股/ETF × 145 组参数，**不采纳**（2026-09-29）

详细的表格与复现命令在 `strategies/弹簧/README.md`；这里只记方法上值得带走的几条。

- **先做事件研究，再跑回测。** 第一版回测胜率只有 13%，与其在单年上试参数，
  不如用宽松条件把几百万个候选形态连同各分量的值一次收齐，离线切片。
  切出来的结果是：每个分量（前期涨幅、阳线实体、支撑均线抬头、顺大势、缩量最狠）
  都与原文预期**方向相反**，2016-2021 和 2022-2026 同号，属于 A 股个股的短期反转。
  这一步 5 分钟，替掉了原本要跑的上百组盲扫。
- **「牛市里弹簧最好」可以证伪。** 把事件按中证500 的趋势状态切成牛 / 熊 / 震荡，
  牛市切片也是负超额，只是负得少一些。
- 🔴 **`sweep.py` 不读策略声明的 `DATALAKE`**：ETF 策略用 sweep 跑时静默落在股票面板上，
  跑出 54 条空仓平线而不报错（2026-09-13 那条失效模式的又一条漏网路径）。
  策略侧已加硬拒（「池子在数据里一只都没有」直接 SystemExit）；sweep 本身未修。
- 🔴 **sweep / run 的 `cast` 会把字符串 `none` 变成 Python `None`**：
  开关的关闭值不要叫 none，用 off。
- 运行期状态**不要在 initialize 里写进 g**：引擎把 initialize 期间写过的名字
  都当成"声明过的参数"。池子、持仓元数据要放到第一次调度时再建。
