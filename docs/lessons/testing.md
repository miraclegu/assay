### ★ 用例要**真跑一次写入**,不能只读已经写好的文件

「结论不存 stats」「去重失效」这两个变异一开始都漏了 ——
因为断言读的是**已经落盘的**结论文件,而那两处改动只在**写**的时候生效。
改成造一个临时 `RUNS` 真调一次 `save_conclusions()`,两条立刻被抓到。

而**结论(meta+stats)只有 6 MB**。

| | 判据 |
|---|---|
| **整目录删** | 同 `(code_sha256, start, end, cash, cost, data_fingerprint, params)` 的多次回测,结果**必然逐位一致**。留最新一次(45 次 / 129 MB) |

🔴 **键里必须带 `data_fingerprint`** —— 不带的话"数据修正前后各跑一次"
会被误判成重复,而那两份恰恰是要留的(实测差 4 次)。

🔴 **完整保留三类**:`picks.json` 标记的(「★ 选中的规则」读它)、
账户绑定版本回测过的(`versions.jsonl` 的 `main_sha256` join
`meta.code_sha256` —— 那是"这个版本回测过没有"的唯一依据)、

★ 最后那条的分界取 `live/accounts.json` 最早的 `created`(本机 2026-09-01),
**不是"最近 N 天"** —— 本机所有归档都在 8~9 月,用"最近 30 天"会把
全部 649 次都保护起来,等于没清。判据要对上"为什么保留"。

🔴 **删了必须留痕,否则"空"与"本来就没有"分不出来。**

### 🔴🔴 守卫【绝不能把生产文件改回去】（2026-09-22，我弄丢了用户一个星）

`picks.json` 那条"不许写生产数据"的守卫原来是「跑前快照 -> 跑完发现变了 ->

★ 这个文件**自己的 docstring 里已经写着正确原则**：

> ⚠ 不盯 `live/`：真实的 serve.py 在后台 tick，它写账本是**它该做的事**，
> 盯了就是天天假报

—— 这句话**对 `picks.json` 一字不差地成立**。作者认出了原则，只是没套到
这个文件上。

**现在：只报不写**（同「对账不一致要报出来、不改写账本」那条 —— 报出来，
别替人决定）。而「测试污染」与「用户在页面上点的」靠**归属**分：

### 🔴 `--all` 要能看到进度（2026-09-22）

两个成因，**缺一条都还是看不到**：

    ① 进度行原来在用例【跑完之后】才打 —— 而最慢那几条各 46~70 秒
      （全量 1083 秒 / 139 条），那几十秒屏幕上一个字都没有，
      分不出"在跑"还是"卡死了"
    ② 重定向到文件时 stdout 是【块缓冲】（攒满 4KB 才落盘），
      `tail -f` 看到的永远是几十条之前的

所以：**开跑之前**就打 `· [25/139] <名字> …　已用 40 秒，约剩 89 秒`，
每行 `flush=True`；终端用回车原地刷新（结果行**精确擦掉**进度行），
重定向单独一行。
🔴 擦除与截断按**显示列宽**算 —— `len()` 数中文按 1 而终端按 2 列，
用它会擦不干净留半行垃圾，截断也会折行，**而折行之后回车根本擦不掉**。
★ 判据走 AST（注释不是 AST 节点）：那个 print 必须**排在调用用例之前**，
  这是"看得到进度"的全部意义。

### 🔴 又一处固定等待：「数据字典页」在全量里 2.9 秒报空（2026-09-24）

全量 149/150，唯一那条是 `数据字典页`：**单跑 6.9 秒通过、全量 2.9 秒报
「侧栏只有 0 条」**。根因不是产品 —— 是 `pg.wait_for_timeout(1500)`：
机器忙的时候那 1500ms 读到的是**半截页面**。

★ 「等固定时间在机器忙时会读到半截表」这条本来就在（持仓表排序那次写的），
  **这里漏了一处**。改成等**条件**（侧栏 ≥ 8 条 且 表格 > 30 行 且 `.dsrc` 在），
  顺带 6.9 秒 -> 3.9 秒。
🔴 **调大那个数不是修法** —— 它只是把阈值往后挪一点，下次机器更忙又会红。
★ 超时要**翻译成原因**：裸 `TimeoutError` 指不到哪一块没出来，现在报的是
  「侧栏 0 条 / 表格 115 行」（变异实测：把 `api_docs` 改成返回空，
  报的正是这一句，一眼看出是侧栏不是表格）。

### 🔴 跑 `--all` 的节奏：阶段边界才跑，短任务先问（2026-09-22 用户定）

`--all` 要 17~18 分钟，所以**不是每改一点就跑**：

| 情形 | 怎么办 |
|---|---|
| 长任务，有**阶段性完成** | 到阶段边界跑一次完整的 |
| **短任务**（改一点点） | **先问用户要不要跑** |
| 一个**大阶段**做完 | 跑一次完整的 |
| 干活期间的日常验证 | 只跑定向的：`-k 关键字` / `--fast` / `--web` |

**Why**：那天我为一个 30 行的改动连跑了四轮（约 70 分钟），其中一轮还是为了
定位"污染源"而重跑的 —— **而污染源是守卫自己**。用户原话：「每次哪怕只修改了
一点点也都要跑一遍好像太贵了」。
★ 这条**不撤销**「改了公共路径要跑全量三层」那条 —— 那条管"真去验的时候
  别漏层"，这条管"什么时候去验"。叠起来就是：**攒到阶段边界，然后一次跑全三层。**

## 自检按【产品域】拆成 `tests/`（2026-09-17，16182 行 -> 入口 40 行）

selftest.py        40 行【入口】：import 五个域 + main()，**命令行一个字没变**
tests/
  _base.py        框架：case/CASES/JQ/_run + 共用辅助（_kset/_kmain/_lp_tab/
                  _via_pop…）+ main()
  test_engine.py  35 条  回测引擎与策略纪律：PIT / 成本 / FIFO / 分红 / 确定性
  test_data.py    13 条  数据平台：面板构建 / 同步与日历 / 字典 / 装配 / 定时
  test_live.py    18 条  实盘：账本与信号 / 业绩与基准 / 模拟盘 / 实盘页
  test_market.py  21 条  看盘：个股 / K 线与指标 / 盘面板块自选 / 买点 / 广场
  test_plat.py    20 条  平台：服务与路由 / 页面框架 / 归档管理 / 拆分守卫

★ 切点与 `srv/` / `lv/` / `views/` **同一判据：按产品域**（用户在做什么），
  不按 tag 分层 —— 按 fast/web/slow 分的话，同一个功能的判据会被拆到两处。
🔴 **拆之前先验了没有顺序依赖**：三个随机种子把 fast 层 62 条、slow 层 11 条
  打乱跑，全绿。按域拆必然改变执行顺序 —— 这个前提不成立的话，拆完会得到
  一堆"单跑通过、全量失败"（本项目为 pyc 缓存栽过同款）。
🔴 **命令行是产品契约**：`python3 selftest.py --fast` 写在 CLAUDE.md、
  launchd 与肌肉记忆里，入口一个字都没改（同「.html 一律留在根目录」
  「`--live` 参数保留」那两条）。

### 拆这一次踩到的三个坑，全是拆 `srv/` 时记过的那几条

| 坑 | 表现 |
|---|---|

| **用例在扫自己的源码** | 三条用例读 `selftest.py` 找 `@case(`（验门面转发覆盖了所有 `sv.xxx`、验哪几条点了「跑一次」必须重定向 `ASSAY_RUNS`、验哪几条写 live/ 必须重定向 `LIVE`）。拆完那个文件里一条 `@case` 都没有了 -> `ValueError: substring not found`。加 `_base._all_case_src()` 返回全部用例源码 —— **import 成功、语法全对，只在那条用例真跑到时才炸**，正是「留在别处的引用」那条的变体 |
| **守卫扫到自己头上** | 新加的「拆分守卫」要找 `dirname(abspath(__file__))`，而**它自己的源码里就有这个字面量** —— 第一次跑就假失败。把它拼出来（同「扫描要跳过守卫用例自己」那条） |

★ 拆完的自证是三层：① **用例清单与 tag 逐条比对**（106 条集合完全一致）；
  ② 全量三层跑绿；③ 新增「自检拆分」守卫用例，钉住这次拆分会烂掉的三种
  方式（入口漏 import 一个域 / 域文件自己定义 `case` / `REPO` 被写回
  `__file__`），**每一种都不报错**，只是静默少用例或路径全错。两条变异验过。
★ 顺带修好了那条「门面转发」用例：它原来只扫 `selftest.py` 里的 28 个

## 🔴🔴 变异测试的还原会被 `__pycache__` 静默吃掉

2026-09-07 实测:变异 `return True` / `return False` **互换位置** ——
字节数完全相同。还原写回时 mtime 落在同一秒、size 也没变,于是 Python 认为
`.pyc` 仍然有效,**继续执行变异态的字节码**。表现是:

- 还原之后全量 selftest **4 个用例失败**(看着像我的改动打挂了东西)
- 单独跑那条用例却**通过**(不同的 import 顺序,恰好重编译了)

★ 教训有三条,都比这个坑本身贵:

## 🔴 断言别写成「字符串出现过」——它抓不到「逻辑被绕过」

今天踩了两次,都是变异测试当场抓出来的:

| 断言 | 为什么无效 |
|---|---|
| `assert 'h.pruned' in js` | 把 `if(h.pruned){` 改成 `if(false){` **照样全绿** —— 提示文本里的 `${esc(h.pruned)}` 也含这个标识符 |
| `assert 'os.kill(pid, 0)' in body` | 那句在 `do_stop` 里有**两处**(轮询 + 强杀后确认),删掉轮询那处照样全绿 |

正确写法是**匹配结构**:`if(h.pruned){`(去空格后)、
或者先把要查的**代码块切出来**再查(`body[index('while …'):index('else:')]`)。
★ 所以变异测试不能只做一遍就算 —— 每条断言都要**单独**变异一次,
  而且要先确认变异**真的写进去了**(有一次我的替换锚点不存在,
  变异根本没生效,看着像"断言通过了")。

🔴 **改了 `assay/*.py` 必须重启 serve.py。** `web/index.html` 是静态文件、
每次请求都从磁盘读；而 Python 模块只在**进程启动时加载一次**。长时间开着的
服务会出现「新页面 + 旧 API」—— 页面去读 API 还没有的字段，
**整屏渲染成 undefined 而不报错**。实测踩过：11:49 启动的服务配 12:53 改的
代码，账户设置里全是 undefined、「流水 undefined」。
现在服务端会把进程启动时间与代码 mtime 报给页面，不匹配就顶部横幅提示重启；
selftest 里有断言（把 `sv._BOOT_TS` 调早来模拟）。

**表单每一项都要有标签**，不能只靠 placeholder —— 字段一取不到值就是个空框，
用户不知道要填什么。设置浮层里有断言：**一个 `undefined`/`NaN` 都不许出现**，
且费率表单必须有「生效日/计费方式/佣金费率/单笔最低佣金/备注」这些标签。

**要横向比较 N 条东西,就得是表格,不能是卡片。** 「★ 选中的规则」原来一条一张
卡(参数一行、8 个指标一行、成本一行)—— 毛病不是挤,是**没法纵向扫**:每张卡
各自排版,同一个指标在不同卡里横坐标都不一样,10 条规则根本比不了。
现在是一行一条的对比表。
🔴 **一张表装所有分组**,不是一组一张 —— 分组各一张 table 时**列宽各算各的**,
上下两个表的"年化"列对不齐,而这一页存在的唯一理由就是纵向比较。
分组是表内的一条带子行(`tr.grp`)。
**能进 tooltip 的就别占列**:本金、成本口径、run_id 都在行的 title 里 ——
十列已经很宽了,再多两列参数就被挤到屏幕外。
但**成本口径的保护不能丢**(本项目两次栽在拿滑点 0 的数字比含滑点的基准上):
与多数行**滑点不同**的那几行挂一个「口径不同」标记,顶部再给一条总提示。
**参数列要有宽度上限且不 nowrap**,否则十几个参数横着排会把指标列挤出屏幕。
数字列右对齐 + `tabular-nums`、点表头排序
(换列时默认方向按**哪边更好**给 —— 年化降序、回撤升序;一律降序会把最差的
排最前面)、宽表自己 `overflow-x:auto`。**排序在组内做** —— 业务域是有意义的
归拢,跨组比较本来就不该发生(区间和基准都可能不同)。
列定义写**一处**(`COLS` 数组),表头/排序/单元格都读它 —— 分三处写迟早
"表头 8 列配 9 个数据",而那不报错,只是整表错位一格。

## 🔴🔴 盘中的判据不能拿"刷新后重新读到的值"当期望（2026-09-15）

「持仓表排序」那条偶发了整整一轮（13 次挂 1 次），我**改了四次判据都没修好**，
最后靠"失败时把现场落盘"一眼看出来：

    603444.XSHG | -1,145.46     ← 这两行"反了"
    600012.XSHG | -1,136.84

排序没坏 —— 这两个只差 **8.6 元**，而实时价每分钟刷一次：
**DOM 是按刷新那一刻的值排的，断言读的是之后的值**。

★ 正确判据：**表里的行序 == 用 `LVO`（渲染时那份数据）自己排一遍**，
  两者同源，不受刷新影响。再配一条**不依赖 `lvSortRows`** 的独立判据
  （用 `LVO` 的数值验行序有序）—— 前者拿那个函数的输出当期望，
  对它内部的改动免疫。
★ 修完 10 连过。**偶发绿的用例比红的更危险**：它让人习惯"重跑一次就好了"。

#### 🔴🔴 同一处第二次偶发 —— 上一版的"修法"把判据换错了方向（2026-09-15）

改成「表里的行序 == `lvSortRows(LVO)`」之后**又偶发**了，而这次的根因是
**那个判据本身与产品规则相反**：`livePatch` 会把 `LVO` 换成**新数据**
（live.js:238），而 DOM **故意不重排** —— "刷新只换数字、不重排"正是
这一页的设计。于是盘中价格一动，"新数据排出来的顺序"就与表里的不同，
**而那不是 bug，是设计**。（表现极具迷惑性：诊断只印前 6 行，两个列表
**打印出来一模一样**却判不等 —— 差异在第 7 行之后。）

★ 正确的分工是**两条路径各自钉各自的规矩**：

| 路径 | 判据 |
|---|---|
| quiet 刷新（`livePatch`） | **行序一字不差**（不许重排）+ `LVSORT` 还在 |
| 全量重渲染（`loadLive`） | 行序 == `lvSortRows(LVO)` —— 这条路径上 LVO 与渲染**同源**，不受刷新抖动影响 |

🔴 **两条都要钉 `LVSORT.k` 非空** —— 只钉行序的话，`LVSORT` 退化成局部
变量时 quiet 路径压根不重排、全量路径两边都回到默认序，**两个断言一起放行**。
★ 变异两条都验过：在 `livePatch` 里把行倒序 → 抓到；把 `LVSORT` 清空 → 抓到。
盘中连跑 8 次全过。
🔴 教训：**判据与产品规则冲突时，先问"产品该怎样"，别急着换一个更"聪明"的
断言** —— 上一版换掉的恰恰是唯一不受刷新影响的那个。
🔴 诊断方法上的教训更贵：我一连猜了四次（负号编码？取错表？解析剥掉了符号？
  半截表？），每次都改完再跑、再偶发。**该在第一次就把失败现场打出来**
  （账户、排序状态、表头、每行原文），而不是靠改判据去试。
★ 顺带记一条：变异测试里出现"漏了"要先问**这个变异是不是无效的**。
  `items.slice().reverse().sort(...)` 没被抓到，查下来是那批数据**没有并列值**
  （`Array.sort` 稳定，reverse 只改并列项的相对次序）—— 那是无效变异，
  不是判据的漏洞。换成"把比较符反过来"立刻被抓到。

## 🔴 偶发绿的用例比红的更危险（同一轮里修的）

「持仓表排序」那条在交易时段 **5 次挂 1 次**，而它与本次改动无关。
根因是判据写成了「刷新前后**行序一字不差**」，而盘中实时价每分钟都在动、
相邻两行的浮盈可能只差几块钱（实测 −1749.00 与 −1754.37 只差 5.37）——
**它们真的会换位，那不是"排序丢了"，是数据变了**。

判据改成两条：刷新之后**仍然按那一列有序** + **行集合不变**。
并把 `wait_for_timeout(1200)` 换成 `wait_for_function(行数 >= 刷新前)` ——
`loadLive` 是异步的，等固定时间在机器忙时会读到**半截表**。
★ 诊断过程本身值得记：我一连猜了三次（负号是 U+2212？取错表？解析剥掉了
  正负号？），每次都改完再跑、再偶发。**该在第一次就把失败现场打出来**
  （账户、表数、列号、每行原文），而不是靠改判据去试。
