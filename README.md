# Assay —— A 股日频回测引擎

> assay: 冶金与化学上「测定矿石或金属的成分与纯度」的检验。
> 策略送进来，测出真实成色。

与数据模块解耦的独立项目。写一个策略文件就能回测，交易规则由引擎负责。

```
finacial/
  datalake/     数据模块（不依赖本项目）
  assay/     本项目（依赖 datalake）
```

**依赖方向单向且不可反转**：`assay` 通过 `assay/feed.py` 读 datalake，
datalake 对 assay 一无所知。datalake 路径不硬编码，由 `ASSAY_DATALAKE`
或 `--datalake` 指定；换数据源只需另写一个实现同样接口的 Feed。

## 用法

```bash
python3 run.py strategies/v0b.py   --start 2019-01-01 --end 2026-06-30 --cash 1000000
python3 run.py strategies/froec.py --start 2016-01-01 --end 2026-08-07 --cash 100000
```

## 写一个策略

```python
from assay.api import *

def initialize(context):
    g.stock_num = 10
    set_slippage(0.0)
    set_order_cost(commission=0.0003, min_commission=5, close_tax=0.001)
    run_weekly(rebalance, weekday=1, time='09:30')

def rebalance(context):
    codes = context.data.codes_at(
        context.previous_date,
        where="is_st = 0 AND floatmv > 0",
        order='floatmv ASC', limit=g.stock_num)
    for c in list(context.portfolio.positions):
        if c not in codes:
            order_target_value(c, 0)
    need = [c for c in codes if c not in context.portfolio.positions]
    if need:
        per = context.portfolio.cash / len(need)
        for c in need:
            order_target_value(c, per)
```

**策略里不写涨跌停、T+1、停牌、退市、整手、税费** —— 那是引擎的职责。
旧引擎把涨停过滤写在选股函数里，那是错的位置：既重复了撮合职责，
又因为只做了买入侧、漏了卖出侧而静默失真。

## 资金与成本：回测时填，不填用业内常用默认值

**成本是【回测参数】不是【策略参数】** —— 同一份策略在不同成本假设下是两次
不同的回测。所以成本不写在策略里，只在命令行给，并完整记进归档的 `meta.json`。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--cash` | **500000**（50 万） | 初始资金 |
| `--slippage` | **0.0015** 双边 | 买 +x/2、卖 −x/2（50~100 万规模的实测标定：每仓 5~10 万时冲击成本近似为 0，集合竞价单一价无买卖价差） |
| `--commission` | **0.00025**（万 2.5） | 当前主流零售费率 |
| `--min-commission` | **5** 元/笔 | 买卖都算 |
| `--stamp-tax` | **auto** | 卖出印花税，**按日期分段** |
| `--volume-ratio` | **0.25** | 单笔委托占当日成交额上限（聚宽同默认）；0 = 不限 |
| `--open-tax` | **0** | A 股买入不征印花税 |
| 红利税 | **开启** | 财税[2015]101号 20%/10%/免；`--no-dividend-tax` 关闭 |

### ⚠️ 印花税默认按日期分段

**2023-08-28 起证券交易印花税减半：千分之一 → 千分之零点五。**
跨越这个日期的回测用单一税率必然错，所以 `--stamp-tax auto`（默认）会自动分段。
要固定税率就传数值，如 `--stamp-tax 0.001`。

### 优先级：命令行显式指定 > 策略内设定 > 默认值

被命令行指定的字段会被**锁定**，策略里的同名设定不但无效，
还会**打印告警**而不是静默忽略 —— 静默覆盖就是下一个「结果对不上却查不到原因」。
运行时成本假设会完整打印在第二行，绝不藏在默认值里。

### 对标聚宽用 `--jq-cost`

一键套用聚宽原版设定（滑点 0、佣金万 3、最低 5、印花税千一**固定**）：

```bash
python3 run.py strategies/小市值/sgmspeg_v0b.py --start 2019-01-01 --end 2026-06-30 \
    --cash 1000000 --jq-cost
```

同一策略两种成本下的差别（实测）：

| 策略 | `--jq-cost`（对标口径） | 默认成本（50 万、真实费率） |
|---|---|---|
| v0b 2019-01~2026-06 | 37.64% | **35.39%** |
| FROEC 2016-01~2026-08 | 38.13% | **37.15%** |

**对标数字和真实预期收益是两回事，不要混用。**

## ★ 面板构建必须是确定的（曾经不是）

**同一份源数据三次重建，FROEC 年化得到 41.31% / 40.73% / 42.52% —— 跨度 1.8pp。**

这比之前查出的任何一个 bug 都更根本：那些是**确定的错误**（错得一致，
所以可以对账、可以归因）；这个是**不确定** ——
我们做过的每一次对比里都含 ±0.9pp 不可归因的噪声。
FROEC 那条「+4.51pp 偏差」的归因分析，有五分之一是在追一个随机数。

### 根因：ASOF JOIN 的右表键不唯一

| 表 | `(code, pub_date)` 重复行 | 占比 |
|---|---|---|
| fin_quarterly | 23,444 | **8.617%** |
| fin_indicator_q | 23,484 | **8.775%** |
| security_status | 3 | 0.025% |

来源是**补披露 / 延迟披露**：`000338` 在 2007-06-28 一天披露 6 个报告期，
`300201` 在 2022-12-13 一天披露 Q1/Q2/Q3。
键并列时 ASOF 取哪一行不确定；而剔除事后重述用的窗口 `ORDER BY pub_date`
在并列时行序任意，运行中最大值也跟着变。

**修法**：三处 ASOF 右表先按 `(code, pub_date)` 去重，同日多期取最新那期。
修完后三次真实重建结果**逐位相同**（37.9846% / 47.4305%），
且 FROEC 偏差从 +4.51pp 降到 **+1.18pp**。

### 附带修的一个更危险的问题：坏面板会被静默使用

面板是**先写盘、后校验**的，所以校验失败时坏数据已经在磁盘上，
只 `sys.exit(1)` 不够 —— 调用方若不检查退出码，下游会在坏面板上跑出
「看着正常」的结果。**我自己就漏过一次**：跑确定性验证时用了
`cd assay && python3 build/build_panel_daily.py`（路径在 assay 下不存在）
并丢掉了 stderr，三次「重建」全是空转，差点得出「已修复」的结论。

现在：校验失败会落 `mart/panel_daily/_FAILED`，`PanelFeed` 直接拒绝加载。
**宁可跑不起来，也不要在坏面板上产出看着正常的结果。**
主键重复时还会打印重复行明细（曾出现过一次不可复现的 1 行重复，
与其盲追，先保证下次能被诊断）。

## 风险警示股：必须用聚宽的【四条】检查

聚宽 `filter_st_stock` 是四条，不是一条：

```python
not is_st  and 'ST' not in name  and '*' not in name  and '退' not in name
```

我们原先只用 `is_st = 0`，而 **149 只「进入退市整理期」的票 `is_st` 是 0** ——
panel 的 `is_st` 由 `public_status IN ('ST','*ST')` 推出，漏了 `'进入退市整理期'`。

**影响远大于行数占比**（2,910 行 / 10.7M = 0.028%）：这些票价格已崩塌、
**流通市值极小，恰好排在「市值升序」最前面**，小市值策略对它们的暴露是最大化的。
实测整理期期间**中位 −17.2%、均值 −20.2%**。

已在 datalake 侧修复，并新增 `is_risk_warned` 列实现完整四条（策略改用它）。
另有约 0.1% 的「正常上市」行名称含 ST/*/退，**只有名称检查抓得到**。

### ⚠️ 一个常量服务两个用途会让修复变成新 bug

`ST_STATUS` 原来同时被用于 **`is_st` 标记** 和 **涨跌停幅度规则**。
实测 002711（欧浦退）在退市整理期 `limit_pct = 0.1`、每天 −10% ——
所以退市整理期是 **10%** 不是 ST 的 5%。
若直接把 `'进入退市整理期'` 加进 `ST_STATUS`，修好 `is_st` 的同时就把涨跌幅改错了。
已拆成 `ST_STATUS`（幅度规则）与 `RISK_STATUS`（风险标记）两个常量，
自检里对**主板**整理期幅度做精确断言（不用全样本均值 0.1182 ——
那是主板 10% 与创业板 20% 的混合，拿它做断言会把两种问题混为一谈）。

### 修复的效果与一个诚实的说明

| | 修前 | 修后 | 聚宽 |
|---|---|---|---|
| v0b | 37.23%（−1.75pp） | **37.95%（−1.03pp）** | 38.98% |
| FROEC | 39.03%（+2.23pp） | **41.31%（+4.51pp）** | 36.80% |

v0b 改善，**FROEC 反而离聚宽更远**。但这不是修错了：

1. 聚宽**同意这个排除** —— 它实际买过的 222 只票里，在买入当日被我们判为风险股的
   有 **0 笔**。
2. 选股命中率几乎没变（85.6% → **85.4%**，494 笔里少 1 笔），
   说明变化不在选股而在**持仓**：修复前，已持有的票进入退市整理期后仍留在目标池、
   被一路持有到 −17%；修复后会被卖掉。
3. 所以 **修前那个 +2.23pp 是「一个真 bug 的拖累恰好抵掉了别处的高估」**。
   修掉拖累后，原本被掩盖的高估显形了。这与之前几次「bug 互相抵消」是同一模式。

顺带一个一致性信号：修复后 v0b 在 100 万本金下**成交量约束 0 笔触发** ——
原先触发那笔是 `002711`（当日成交额 3 千元），现在已被风险过滤挡在上游。
两个修复自然咬合。

## 股票名称必须取自专用名称历史表

界面上交易记录 / 持仓 / 拒单都显示 **`名称(代码)`**，且是**当时**的名称 ——
拿当前名称标一笔 2016 年的交易是误导（002711 走过
欧浦钢网 → 欧浦智网 → ST欧浦 → *ST欧浦 → 欧浦退）。

### ⚠️ 数据源踩过一个坑

原先 panel 的 `sec_name` 取自 `security_status.name`，而**那张表只在
【状态】变化时才有新行** —— 公司改名而状态不变时，它的 `name` 就停在旧值。
实测 2024-06-28 有 **888/5088 行（17.4%）**与权威名称不符：

| 代码 | `security_status` 里的旧名 | 权威名称 | 状态 |
|---|---|---|---|
| 688109 | 品茗股份 | **品茗科技** | 正常上市 |
| 600929 | 湖南盐业 | **雪天盐业** | 正常上市 |
| 600963 | 岳阳纸业 | **岳阳林纸** | 正常上市 |

已改用 `std/security_name`（专用名称历史表，`valid_from`/`valid_to` 区间）。

### 这不只是显示问题

`is_risk_warned` 的名称检查用的正是那个过期字段，结果**漏判了两只欺诈退市股**：

| 代码 | 过期名 | 真实名 | 窗口 |
|---|---|---|---|
| 300372 | 欣泰电气 | ***欣泰** | 2016-07~08 |
| 300028 | 金亚科技 | ***金亚** | 2018-06~08 |

两只都是 `正常上市` 状态（所以状态表没有新行），而它们正是小市值策略会买的
—— 暴跌后流通市值极小，排在「市值升序」最前面。

**核对过聚宽真实成交：这两只它从未买入**（交易记录覆盖 2016-01~2021-03，
两个窗口都在范围内），即我们的排除与聚宽一致 —— 修复方向是对的。

### 实现：服务端按需 join，不写进归档

名称在归档时**不**写入 parquet，而在服务端按行日期解析。这样
**24 次已有归档立刻都能显示名称、不必重跑回测**，归档文件也不为一个展示字段膨胀。
名称区间平均 2.5 段/只（14,258 段 / 5,668 只），线性扫描足够。

三个表各取各自合适的时点：交易记录用**建仓日**（一笔交易的身份以建仓时为准）、
持仓用**快照当日**、拒单用**下单当日**。

## 涨跌停算不准的日子

面板自带 `limit_rule_ok`，标出「本行涨跌停价算得准不准」（用实际 high/low
与算出的涨跌停价对拍）。2016 年后 **0.0229%**（2,458 行）为 false：

| 类别 | 行数 | 股票数 | 真实规则 |
|---|---|---|---|
| **上市首日** | 1,474 | 1,474 | 主板 IPO 首日 +44%/−36%；科创/创业注册制无限制 |
| 上市 1–5 日 | 496 | 381 | 科创板/创业板注册制前 5 日无限制 |
| 其它 | 320 | 300 | — |
| **退市整理期（首日）** | 105 | 105 | 首日无涨跌幅限制，之后 10% |
| ST/*ST | 63 | 57 | — |

**引擎侧已修**：`can_trade` 现在尊重这个标记 ——
拿一个已知算错的涨跌停去拦交易，比不拦更糟（这些日子本就多是「无限制」，
即不存在涨跌停）。

### ⚠️ 诚实说明：这个修复当前不改变任何结果

实测 `limit_ok = false` 的行里，涨跌停标记**从未为真**（同时满足
`limit_ok=false` 且 `open_limit_*=true` 的行 **0 个**）——
因为 `is_open_limit_up` 要求开盘价精确等于算错的涨停价，本来就撞不上。
两条策略的基线也逐位不变。

所以它是**纯防御**：一旦 panel 补上 IPO 首日等规则、标记可能变真，它才会生效。
自检里用合成 bar 验证守卫本身有效，而不是靠历史数据碰运气。

### panel 侧的规则细化：待做，且要逐条实证

明确的规则（era 相关，**每条都该像 2026-07-06 主板 ST 那次一样用数据验**）：

| 情形 | 规则 |
|---|---|
| 主板 IPO 首日（2014 起） | +44% / −36% |
| 科创板 sh68 上市前 5 日 | 无涨跌幅限制 |
| 创业板 sz30 注册制（2020-08-24 起）前 5 日 | 无涨跌幅限制 |
| 创业板核准制（2020-08-24 前）首日 | +44% / −36% |
| 退市整理期首日 | 无限制；之后 10% |

「无限制」应表达为 `limit_up/limit_down` 为 NULL、`is_limit_*` 为 false，
而不是套一个错的百分比。

**当前不做的理由**：只影响 0.0229% 的行，而我们两条策略（`listed_days > 250/375`
＋风险股过滤）根本不碰这些行；而逐条实证 era 规则的成本不低。
等有打新/次新股策略时再做 —— 那时它就是必需的。

## 停牌持仓：可见而不折价

停牌期间持仓按**最后已知的后复权收盘价**挂账（否则市值会直接归零 ——
那是旧引擎的一个 bug）。

### ⚠️ 不加折价，而且这是被数据否掉的一个假设

原本的计划是「超阈值折价」，前提是「长期停牌股复牌常大幅下跌」。
**实测把这个前提否掉了**（2016 年后全市场，停牌 >10 天的复牌日收益）：

| 停牌时长 | 次数 | 复牌收益中位 | 均值 | P10 |
|---|---|---|---|---|
| 11–30 天 | 21,147 | **+0.14%** | −0.41% | −9.99% |
| 31–90 天 | 661 | −4.49% | −9.69% | **−57.97%** |
| 91–180 天 | 747 | −3.18% | −0.85% | −10.01% |
| 181–365 天 | 261 | −5.02% | −1.72% | −10.02% |
| >365 天 | 42 | −9.91% | +22.01% | −10.71% |

中位只有 −3%~−5%（11–30 天甚至微涨），**而且那笔损失在复牌当天本来就会计入** ——
再加折价就是双重计算。31–90 天那档有 P10 −57.97% 的左尾，但那是尾部不是中枢。

### 真正的风险是「永不复牌又没有退市日」

那种情况会**永久按陈价挂账、把权益虚高地钉在那里**。所以做法是
**可见 + 期末响亮告警**，而不是折价：

```
停牌挂账             360 持仓日   最长连续 143 天 (000862.XSHE)
⚠ 期末仍有 N 只停牌持仓（按陈价计入权益，最终收益不可验证）
```

实测 FROEC 冻结 360 个持仓日（约占 1.5%）、最长 143 天、**期末 0 只仍冻结**；
v0b 只有 1 个持仓日。所以在当前两条策略上这个风险并未实现 ——
但没有可见性的话，下一条策略上出问题也不会有人发现。

`frozen_days` / `max_frozen_run` / `n_frozen_at_end` 已进 `stats.json`。

## 成交量约束与资金容量

单笔委托最多吃掉当日成交额的 `volume_ratio`（默认 **0.25**，与聚宽
`order_volume_ratio` 同默认）。买卖两侧都受限，超出部分**部分成交并留痕**。

用 `amount`（元）而不是 `volume` 计算 —— ⚠️ 实测面板 `volume` 的单位是
**「股 × 100」**（除以 100 才是股数：交叉验证 `volume/100` 算换手率得 0.4731，
面板 `turnover` 列 0.473107，精确吻合）。用元对元绕开这个单位陷阱。

### v0b 资金容量曲线（2019-01~2026-06，滑点 0）

| 初始资金 | 不限量年化 | 限量后年化 | 差 | 被削笔数 |
|---|---|---|---|---|
| 50 万 | 37.57% | 37.37% | −0.20pp | 2 |
| 100 万 | 38.47% | 37.23% | −1.23pp | 6 |
| 500 万 | 35.93% | 36.52% | +0.59pp | 69 |
| **2000 万** | 37.04% | **30.23%** | **−6.81pp** | 493 |
| **5000 万** | 35.64% | **22.29%** | **−13.35pp** | 645 |
| **2 亿** | 35.68% | **8.80%** | **−26.88pp** | 664 |

**没有这个约束，回测在所有资金规模上都报 35~38%** —— 等于宣称策略可以无限扩容。
这就是它防止的假结论。v0b 的真实容量大约在 **500 万~2000 万**，2 亿基本失效。
（500 万那格 +0.59pp 是整手取整的路径混沌，不是信号。）

### ⚠️ 曾判断「实测永不触发」而不实现 —— 那个判断错在只看中位与 P90

当时测的是「委托占当日成交额」：中位 0.02~0.44%、P90 最高 1.15%、无一笔超 25%。
但**约束这种东西只有尾部重要**。v0b 全区间只有 **6 笔**被削，却值 **1.23pp** 年化。
被削的都是极端情形：

| 日期 | 代码 | 当日成交额 | 流通市值 | 换手率 |
|---|---|---|---|---|
| 2021-06-07 | 002711（后退市） | **0.3 万元** | 5.26 亿 | 0.00% |
| 2024-06-11 | 600306 | 147 万 | 1.20 亿 | 1.23% |
| 2026-06-08 | 600421 | 432 万 | **0.65 亿** | 6.61% |

第一笔尤其说明问题：一只**当天只成交 3 千元**的票，旧引擎会让你买入 10 万。
这些全是极微盘 + 极低流动性 —— 正是小市值策略的核心持仓类型。

### 对标口径的影响

开启后 v0b 从 38.47% 降到 37.23%（聚宽 38.98%，偏差 −0.51 → **−1.75pp**），
离聚宽更远。但**聚宽的 `order_volume_ratio` 默认也是 0.25**，所以差异更可能来自
那 6 天两边持仓不同，或聚宽按 volume(股) 而非 amount(元) 计。
默认保持开启 —— **忠于真实机制优先于凑指标**。
FROEC（10 万本金）0 笔被削，不受影响。

## 分红：现金真实入账（后复权口径内的精确模型）

后复权价隐含「分红自动再投资」。只记税不动仓位，`cash` 与持仓市值的拆分就和
现实不同 —— 现实里分红是真现金，策略若用 `portfolio.cash` 定仓位会与实盘有差别。

除权日把仓位的一小部分「卖成现金」：

```
frac   = dps / close_raw(t-1)
cash  += shares × close_hfq(t-1) × frac        # 恰等于 真实股数 × dps
shares = shares × (1 - frac)
```

**这是精确模型不是近似** —— 真实股数守恒：

```
real_new = shares(1-frac) × factor(t) = shares(1-frac) × factor(t-1)/(1-frac)
         = shares × factor(t-1) = real_old        ✓ 现金分红本不改变股数
```

⚠️ **`entry_price` 不缩。** 缩了会把分红错记成价差收益：买 100 单位@10、
分红 frac=2%（现金 +20、股数 98）、股价未动@10 卖出 ——
不缩得 `pnl = 98×(10−10) = 0`（价格贡献 0、分红贡献 20，归因干净）；
缩到 9.8 得 `pnl = 19.6`（凭空出现价格涨幅）。总额都对，但归因错了。
`trades` 里的 `ret`/`pnl` 只反映**价差**，分红单列 `div_gross`。

改完的影响：v0b 37.64% → **38.47%**（聚宽 38.98%，偏差 −1.34pp → **−0.51pp**）。
往聚宽靠近，是模型正确的旁证 —— 说明聚宽也按现金入账而非自动再投资。
FROEC 38.13% → 39.03%（偏差 +1.33 → +2.23pp），方向相反，但**忠于真实机制
优先于凑指标** —— 与 ntile→floor 那处同一原则。

## 加减仓：内置在买卖函数里，FIFO 分批持仓

```python
order_target_value(code, 12000)    # 调到目标市值；已持仓则加仓/减仓
order_target_percent(code, 0.1)    # 调到总权益的 10%；0 即清仓
```

**加减仓不另开路径** —— 与「唯一卖出出口」同一原则：买卖各自只有一个成交函数
（`_buy` / `_fill_sell`），加仓是往 `lots` 追加一批，减仓是 FIFO 消耗若干批。
滑点/佣金/印花税/红利税/交易日志因此天然只写一遍。

### 为什么分批（FIFO）而不是合并成平均成本

| 规则 | 合并平均成本的后果 |
|---|---|
| 红利税按持有期分档（≤1月 20% / 1月~1年 10% / >1年 免） | 分档静默算错 |
| T+1 只锁**当日买入**的部分 | 要么全锁要么全不锁，都不对 |

分批之后两者都能**精确**计征，不需要「按卖出比例摊」这类近似。
每笔平仓记录带的是**该批**的建仓日、建仓价、持有天数 ——
所以 `trades.parquet` 里同一天同一只票可能有多行（FIFO 消耗了多批）。

手续费按**整笔委托**算一次（min-5 是每笔而非每批），红利税按批加总。

### 写目标权重类策略要注意两件事

1. **留现金缓冲**（主要因素）。按 100% 权益分配目标市值，而手续费与滑点又要
   从权益里出，最后一只必然差钱。这是目标权重类策略的固有约束，不是引擎问题。
2. **先减后加**（次要，但原理正确）。同一循环里边加边减，靠前的票会先把现金花光、
   靠后的还没减仓回收。

受控测量（v0b 同区间、月频等权再平衡）：

| 变体 | 年化 | 拒单 | 现金不足 |
|---|---|---|---|
| A 混合单循环 + 100% | 23.25% | 81 | 72 |
| B 先减后加 + 100% | 23.18% | 78 | **69**（只省 3 笔） |
| C 先减后加 + 99.5% 缓冲 | 23.40% | 68 | **58**（再省 11 笔） |

⚠️ **先减后加只省 3 笔，起决定作用的是现金缓冲。** 一开始把 69 笔归因给
「混合循环」是错的 —— 那 69 笔在两种写法下都存在。原因是「清掉非目标持仓」
本来就已是独立的第一个循环，混合只发生在**目标票之间**，而它们大多是延续持仓、
权重接近，加减金额都很小。目标集变动大或权重很不均匀（如按股息率加权）时，
先减后加才会真正重要。

剩余的 58 笔来自「非目标持仓因跌停/停牌卖不掉、现金没回收」加整手取整残差。
引擎在这种情况下**拒单而不是让现金变负**，这才是关键。

`strategies/_demo/rebalance_weights.py` 是可运行的示例（月频调回等权）。
它跑出来的 **最大权重均值 11.1% / 峰值 18.6%**，而不再平衡的 v0b 是 12.1% / 20.5%
—— 集中度指标直接反映了两种做法的差别。

## 参数扫描

```bash
# 滑点敏感性
python3 sweep.py strategies/小市值/sgmspeg_v0b.py --start 2019-01-01 --end 2026-06-30 \
    --cash 1000000 --grid slippage=0,0.0015,0.003,0.005

# 策略参数 × 成本参数（笛卡尔积），每个组合自动归档
python3 sweep.py strategies/小市值/sgmspeg_v0b.py --start 2019-01-01 --end 2026-06-30 \
    --cash 1000000 --jq-cost --grid stock_num=5,10,20 --grid candidate_num=15,30
```

单次回测也可以覆盖策略参数：`run.py ... --param stock_num=20`（可重复）。

### 两个实现要点

- **feed 只物化一次、跨组合复用** —— 物化 bars 表是最慢的一步（全区间约 20 秒），
  9 个组合各建一次就是 3 分钟纯浪费。
- **参数名拼错立即抛错**并列出可用参数 —— 静默无效会让扫描结论变成
  「这个参数没影响」，那是最危险的一类假结论。

### 并行：`--jobs N`

策略函数走 api 的模块级代理（为了照抄聚宽的裸函数手感），有全局状态，
所以**同进程内不能并发**。用多进程绕开 —— 每个子进程独立导入 assay、
各自持有一份 api 状态。worker 用 initializer 建**一次** feed 后复用，
而不是每个组合建一次。

实测（v0b 2019-2026 全区间，4 进程）：

| 组合数 | 串行 | `--jobs 4` | 加速 |
|---|---|---|---|
| 4 | 30.4s | 17.3s | 1.76× |
| 8 | 52.0s | 31.4s | 1.66× |

**加速比明显低于 4× 且不随组合数改善** —— 瓶颈是**核心争用**而非 feed 物化：
DuckDB 本身就在用多核（串行时 CPU 已达 525%）。所以 `--jobs` 是有用但有限的优化，
组合数少于 `jobs` 时没有收益，内存也按 worker 数放大（全区间 bars 表约 5M 行/进程）。

**不变量（已进自检）**：并行结果与串行**逐位相同**，且最终表格重排回**网格顺序** ——
并行时结果按完成顺序返回，要看的是趋势，顺序不能乱。

归档目录创建改为原子（`makedirs(exist_ok=False)` + 捕获 `FileExistsError` 递增）——
原先「先 exists 再 makedirs」是 check-then-act 竞态，多进程会拿到同一个名字。

### 输出保持网格顺序，不按收益排序

要看的是**趋势**，按收益排序会把单调性打乱。实例（v0b 滑点敏感性）：

| slippage | 年化 | 超额年化 | 信息比率 | 年换手 |
|---|---|---|---|---|
| 0 | 38.13% | 24.58% | 1.043 | 7.658 |
| 0.0015 | 37.06% | 23.61% | 1.007 | 7.745 |
| 0.0030 | 35.20% | 21.94% | 0.951 | 7.772 |
| 0.0050 | 32.78% | 19.76% | 0.876 | 7.789 |

**可交叉验证**：换手 7.7 次全仓往返/年 → 预测 `1.3813/(1+7.7×0.005)−1 = 33.0%`，
实测 32.78%。成本-收益的线性外推成立。

二维扫描能直接看出**参数间的交互**：`candidate_num` 只在 `stock_num=20` 时才有影响
（候选 15 只填不满 20 个仓位）。以前这种关系得手工推。

### 数据版本指纹

`meta.json` 里除代码哈希外还记 `data_fingerprint`：

```

    panel    28ba4cbe4100  24 文件 / 1190.0 MB / 最新 2026-08-26T10:02:56
    std      598dd20a0d2b  12 文件 /   46.2 MB / 最新 2026-08-26T10:01:43
    index    af9108dd8438  24 文件 /   61.5 MB / 最新 2026-08-25T22:37:59
```

**没有它，panel 重建一次、同一份策略结果就会变，而归档里看不出来** ——
这是「代码哈希」在数据侧的对应缺口。分部件给哈希，`diff` 才能指出
**哪一部分**变了，而不只是「变了」。

⚠️ 取舍：用 `(相对路径, 字节数, mtime)` 而不是内容哈希 —— panel 有 4GB+，
每次回测算内容哈希不可接受。代价是「重建出内容完全相同的文件」会被误报为变了，
但这个方向是安全的：**宁可误报，不可漏报**。要逐字节确认时再单独跑内容哈希。

`runs.py diff` 会把归因的第一个岔路口直接摆出来：

```
✓ 策略代码相同。
✓ 数据版本相同。
· 策略参数不同: {'stock_num': 10}  vs  {'stock_num': 20}
```

旧归档没有指纹时如实说「无法判断数据是否变过」，不假装通过。

`run_id = 时间戳-代码哈希前6位`。**带代码哈希是为了区分「同一份代码重跑」
和「代码改了再跑」** —— 只看时间戳分不出来，而归因时这恰恰是最先要确认的事。

#### ★ 策略身份：两个哈希，职责不同

「代码版本」（⌗）是独立的一层，而不是回测表里的一个列 —— 不同版本的回测
放在一起比较是没有意义的。只有一个版本时**跳过这一层**，免得多点一次。

版本用哪个哈希，经过一次修正：

| 哈希 | 算法 | 用途 |
|---|---|---|
| `semantic_sha256`（**分组用**） | `ast.parse` 后哈希 `ast.dump(tree)`，剥掉 docstring 与 `NOTE` | 版本层按它归并 |
| `code_sha256`（**审计用**） | 文件原始字节 | 归档里躺的是哪份字节，一字不差 |

最初只有字节哈希，规则是「改一个字符就是另一个策略」。实践中它太严：
给四个策略加 `NOTE`、修被拼接的注释、调排版，每次都**实测精确复现原数字**
（5.71 / 10.27 / 14.15 / 14.55，行为完全没变），却各新增一个版本节点。

改用行为哈希后判别边界（`selftest.py` 两侧都断言）：

| 改动 | 判定 |
|---|---|
| 行内注释 / 加注释行 / 空行排版 / `NOTE` / docstring | **同一版本** |
| 阈值、持仓数、选股逻辑、任何影响结果的改动 | 新版本 |
| **SQL 字符串内**改注释或加空格 | **新版本**（见下） |

要点：

- **注释根本不在 Python AST 里**，所以改注释天然同哈希，不需要特殊处理。
  docstring 在 AST 里（是字符串字面量），显式剥掉。
- **`NOTE` 必须剥掉**，否则循环依赖：改简介 → 新版本 → 又要写新简介。
- **刻意不对 SQL 做归一化**：那需要 SQL 解析器，一旦弄错会把真实逻辑改动
  误判成同一版本 —— 那比多几个版本节点危险得多。宁可多分几个版本。
- **字节哈希不能丢**。它是「当时执行的确切代码」这个保证的载体，
  也是归档自包含的基础。同一语义版本下有多份字节版本时，
  版本行标 `N 份字节版本`，版本页列出它们、可逐份查看源码。
- 旧归档**不必重跑**：语义哈希可从归档的 `strategy.py` 快照现算，
  `meta.json` 里有记录的直接用。

#### 三个实现决定

**1. 仅标准库**（`ThreadingHTTPServer`）。装 Flask 只为一个本地看板不值得，
多一个依赖就多一处「环境不一致导致跑不起来」。

**2. 图表手写 SVG，不用 CDN。** 本项目已被静默失败坑过多次 ——
CDN 加载失败就是白屏，离线时完全不可用。权益曲线本质是一条 polyline，手写足够。

**3. 净值曲线默认对数坐标。** FROEC 累计 2960%，
**线性坐标会让前几年完全看不见**。可一键切线性。

#### 界面自身也有回归测试（playwright）

**JS 语法检查过不代表能渲染** —— 运行时错误在终端里看不到。
自检里用真实浏览器跑一遍：目录树 → 展开 → 点进详情 → 九个页签逐个渲染 →
返回目录 → 浏览器后退，并断言 **0 个 JS 错误**。
playwright 或浏览器不可用时优雅跳过，不让环境差异变成假失败。

#### 两处「不靠估、靠量」

- **表格表头**：`.tw` 自己是滚动容器，所以 `th` 必须 `top:0` 贴容器顶部。
  原先写 `top:52px`（那是给整页滚动准备的偏移），把表头整体往下推了 52px。
- **日期分隔行的吸顶位置**取决于表头实际高度（字号/padding/浏览器都会影响）。
  我先估了 23px，**playwright 量出实际是 27px** —— 差 4px 就会重叠。
  改成渲染后量出来写进 CSS 变量，实测日期块与表头底 gap 恰好 0px。

两处都由自检守住：滚动后断言 `th` 距 `.tw` 顶部 ≤2px（含 1px 边框）。

#### 两个必须留意的正确性细节

- **持仓 22k 行不一次发**，分页返回（默认 100 条/页，上限 500）——
  全量塞给前端要渲染 22k 个 DOM 节点，是「能跑但很慢」的典型。
  不变量：**日期倒序且同日相邻**（前端按日期变化插分隔块，靠的就是这个），
  越界 offset / 超限 limit 自动收敛而不报错 —— 三条都进了自检。
- **`run_id` 来自 URL，只接受归档索引里存在的值**，绝不直接拼路径。
  自检覆盖 5 类非法输入（目录穿越、SQL 片段、不存在的 id、空值），全部必须 404。

为基点（与聚宽一致）。两者口径不同，界面上直接写明 —— 不让读者自己猜。

## 引擎负责的 10 条 A 股语义

每一条都是拿聚宽实测结果逐年对账反推出来的，
**每一条都曾以静默方式让回测失真**（不报错、不为空、结果看着完全合理）：

1. **后复权计价** —— 用不复权价算权益会让除权日凭空蒸发、分红送转不入账
2. **停牌持仓估值** —— 缺行时若按 0 计，停牌持仓市值直接消失
3. **停牌不能交易** —— 面板缺行即当日无法成交
4. **退市 vs 停牌** —— 判据必须是权威 `delist_date`，不能拿「缺行 N 天」当代理。
   ⚠️ `delist_date = 2200-01-01` 是「未退市」哨兵值，不剔除会把在市股票判成已退市
5. **整手约束按真实股数** —— 套在后复权价上等价于要求后复权价 < 单仓资金/100，
   老股票（因子 20~30）会被整只静默跳过
6. **开盘涨停买不进 / 开盘跌停卖不掉** —— 一字板无对手盘
7. **T+1** —— 当日买入不可卖出
8. **红利税按持有期在卖出时补缴** —— 财税[2015]101号 20%/10%/免；
   聚宽会扣，默认开启
9. **印花税卖出千一 + 佣金双边万三、最低 5 元/笔**（min-5 买卖都算）
10. **滑点双边**（聚宽 PriceRelatedSlippage 语义：买 +x/2、卖 -x/2）

**拒单全部记录在 `broker.rejects` 并在报告里按原因分类打印** ——
不静默丢弃。旧引擎的一系列 bug 之所以难找，就是因为失败是无声的。

## 基准与绩效指标

```python
def initialize(context):
    set_benchmark('000905.XSHG')      # 聚宽代码或 tdx 代码(sh000905)
```

命令行 `--benchmark` 优先于策略内设定（同成本参数的规则，冲突时告警）。

给出：**超额收益 / 超额年化 / 超额收益最大回撤 / 信息比率 / alpha / beta**
（这些聚宽结果里都有，没有基准就只能比年化，归因粒度太粗），
以及 索提诺 / 卡玛 / **年换手（次全仓往返）** / 平均持有天数 / 胜率 / 盈亏比 /
费用合计 / **持仓集中度（最大权重均值·峰值·HHI）**。
`--monthly` 打印月度收益表 —— 看「哪一年哪个月崩的」比看一个总回撤有用得多。

### ⚠️ 基准基点必须取回测首日的【前一交易日】收盘

实测：聚宽 FROEC 报的基准收益 **4.76%** = 中证500 从 **2015-12-31** 到 2026-08-07。
用首日（2016-01-04）收盘做基点得 **14.27%** —— 差 9.5pp，
因为 2016-01-04 是熔断日（−8.99%），用首日收盘等于把它排除在基准之外。
**与「回测首日不调仓」是同一类边界差一天的错。**

同理，日收益序列把初始资金作为第 0 点，否则**回测首日的收益不会进入序列**，
夏普 / 波动 / beta 全都会漏掉第一天。

### FROEC 全指标对标（2016-01-01~2026-08-07，10 万，`--jq-cost`）

| 指标 | assay | 聚宽实测 | 差 |
|---|---|---|---|
| **基准收益** | **4.76%** | **4.76%** | **0.00** |
| **beta** | **0.898** | **0.899** | ≈0 |
| **alpha** | 35.21% | 36.0% | −0.8pp |
| 年化 | 38.13% | 36.80% | +1.33pp |
| 最大回撤 | 47.94% | 47.24% | +0.70pp |
| 超额收益最大回撤 | 45.78% | 44.54% | +1.24pp |
| 胜率 | 61.38% | 61.9% | −0.5pp |
| 夏普 | 1.24 | 1.083 | +0.16 |
| 信息比率 | 1.55 | 1.441（超额夏普） | +0.11 |

**beta 对到小数点后三位、基准收益逐位相同** —— beta 是对整条收益路径回归得到的
系数，撞这么准不是运气，这是目前最强的引擎忠实度证据。
另：v0b 年换手 7.59 次/年，而从聚宽交易记录实测是 7.7 次/年，独立吻合。

⚠️ 盈亏比 1.46 vs 聚宽 2.790 差得多，但**这是定义差异不是偏差** ——
本项目算的是「盈利交易平均收益率 / 亏损交易平均收益率」，

## 时刻是「逻辑阶段」，不是真实时钟

| `time=` | 阶段 | 成交价 |

## 新旧引擎对账：各修一处，方向相反

用归档的 `holdings.parquet` 逐日比对持仓，首个分歧日 **2019-04-15**。
差异根因是**黑名单与截断的先后顺序**：

| | 顺序 | 后果 |
|---|---|---|
| 旧引擎 | select 内部先 `[:10]`，主循环再剔黑名单 | 目标缩到 9 只，**名额丢掉** |
| 聚宽 v0b | 候选 15 → 可交易过滤 → 黑名单 → **最后**截到 10 | 被剔的候选由下一名**补位** |

→ **旧引擎有 bug，新引擎的顺序才对。** 已确认聚宽源码：
`g.target_list = g.target_list[:min(g.stock_num, len(g.target_list))]` 在黑名单之后。

⚠️ 但两条线的原版写法**不同**，不能互相照抄：
- **v0b**：`candidate_num=15`，不预截断 → 过滤 → 黑名单 → 截到 10（**补位**）
- **FROEC**：`get_stock_list(context)[:10]` **先截到 10** → 过滤 → 黑名单（**不补位**）

同时新引擎也有一处不忠实：聚宽在策略里做 `filter_paused/limitup/limitdown`，
涨停的候选会被**替换**；我原先全交给 broker 拒单，名额直接丢了。
修法见下 —— 补上后 FROEC 从 42.17% 降到 38.13%，差距从 +5.37pp 收到 +1.33pp。

### 「能否成交」与「选股要不要补位」是两件事，但判据必须同一份

`Broker.can_trade(code, side)` 是规则的**唯一**实现处：
- 撮合走它（硬约束，违反就拒单并留痕）
- `context.tradable(codes, side)` 也走它（策略预筛，对应聚宽的三个 filter_*）

这样策略能决定「用不用下一名补位」这个**选股策略**问题，
而「能不能成交」这个**撮合规则**问题只有一份实现 ——
旧引擎正是因为把涨停过滤写进选股、买入侧做了卖出侧漏了，才长期静默失真。

## 为什么不改用不复权数据

「引擎既然能正确处理分红拆股，是不是可以直接用不复权数据？」——
不复权在建模上确实更忠实（现金是真现金、股数是真股数、整手与涨跌停价天然正确），
但代价是 **correctness 负担的转移**：

| | 后复权 | 不复权 |
|---|---|---|
| 送股/转增/配股 | 复权因子已编码好 | **必须自己显式处理** |
| 依赖的数据 | 一列 `hfq_factor` | 完整的公司行动表 |

⚠️ **一处已撤回的论证**：我曾用「面板上 35,189 次因子跳变有 505 次（1.4%）
在分红表里找不到对应事件」来论证「复权因子比公司行动表更完整」。
**这个证据是错的** —— 那 505 次几乎全是**检测方法的伪影**：

送转发生在**停牌期间**，因子在真实除权日就变了，但面板在停牌期没有行，
用 `lag(hfq_factor)` 比较就把变化归到了**复牌日**，复牌日当然对不上任何事件日期。
逐案核对（幅度最大的 5 个）：

| 代码 | 停牌区间 | 因子跳变日 | 转增除权日 |
|---|---|---|---|
| 300450 | 2016-03-11 → 2016-07-20（131天） | 2016-07-20 **复牌日** | 2016-03-29（停牌期内） |
| 002712 | 2016-04-08 → 2016-08-17（131天） | 2016-08-17 **复牌日** | 2016-06-17（停牌期内） |
| 600733 | 2018-02-01 → 2018-09-27（238天） | 2018-09-27 **复牌日** | 2018-09-19（停牌期内） |

孤儿跳变 83% 集中在 2016–2018，正是停牌率 9% 的那几年 —— 与该解释一致。
**分红表里这些事件都有，1.4% 的「缺口」不存在。**

### 那么现在为什么还不改用不复权

剩下三条理由，都比原来那条弱，但仍成立：

1. **配股（rights issue）覆盖未验证** —— 它不在分红表里，是另一类公司行动。
   改用不复权前必须先确认这类事件的数据完整性。
2. **重新推导已被推导过的东西** —— 复权因子是数据方用完整公司行动算出来的；
   自己再算一遍等于多一处可能出错的地方，而收益只是「账面更像实盘」。
3. **后复权对「跨停牌的公司行动」天然免疫** —— 就是上面那个案例：
   送转发生在 131 天停牌期内，后复权只需要因子；不复权则必须显式处理
   「停牌期间股数变了」，而那正是最容易漏的情形。

**结论不变（暂不改），但依据换了 —— 原来那条依据是我的检测伪影，已撤回。**

**但不必二选一。** 分红现金流可以在后复权口径内精确建模 ——
除权日把仓位的一小部分「卖成现金」：

```
frac   = dps / close_raw(t-1)
cash  += shares × close_hfq(t-1) × frac      # 正好等于 真实股数 × dps
shares = shares × (1 - frac)
```

既拿到真实现金入账，又不用重新推导公司行动。而且**它会改变结果**：
分红从「自动再投资」变成「躺在现金里等下次调仓」，对红利策略是实质差别。
